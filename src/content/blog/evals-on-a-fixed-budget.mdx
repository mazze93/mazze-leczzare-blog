My eval was finished except for the part that costs money. The harness for [js-yaml-dos-eval](https://github.com/mazze93/js-yaml-dos-eval) passes its self-tests and its end-to-end pipeline tests, and the README says, accurately, that no model has been run against it yet. The obvious next step was "run five models for five epochs." The obvious next problem was paying for that.

So I worked out what a credible result requires, and it turned out to be much less than that. This is the playbook I ended up with. It assumes [Inspect AI](https://inspect.aisi.org.uk/) and an eval whose scorer is code: execution, matching or measurement, with no model grading another. Prices, free tiers and credit programs were checked in November 2026. They change, so check them again before you plan around them.

## Where the money goes

Model calls are the only step that costs money, and you only have to pay for each output once. Everything after generation can be free and repeatable.

1. **Output tokens dominate.** Prompts are usually short and cacheable. Long completions (code, payloads, reasoning) are where the bill comes from. Measure tokens per call on one sample before you commit to a run.
2. **Generation and scoring are separate steps.** Generate with `--no-score`, then score later with `inspect score`. You can fix the scorer, or re-run a timing scorer on an idle machine, without calling the model again.
3. **There are two kinds of noise.** Sampling variance comes from the model and needs more epochs, which cost money. Scorer noise, like wall-clock timing, needs more scoring passes, which are free. Buying epochs to smooth out a stopwatch spends money in the wrong place.
4. **Cache everything.** Inspect's local cache serves identical requests for free, so a crash or a rerun after a code fix shouldn't bill you twice.
5. **Batch whatever can wait.** Batch APIs cost about half, in exchange for results that can take up to a day.
6. **Debug on free models; pay for runs you'll publish.** Prompt, parser and scorer bugs cost nothing to find on a local model.
7. **Small n is fine if you say so.** Ten samples with honest error bars are worth more than a hundred with a hidden flaw.

## What each budget buys

At $0 you can publish a complete, honest results table on open-weight and free-tier models. Money buys two things: rows for frontier API models, and the sampling variance you can only measure with repeated epochs.

| Budget | What it buys | What you can't claim |
| --- | --- | --- |
| $0 | Local open-weight models, free API tiers, one manual chat row | Anything about frontier API models under controlled conditions |
| $10, once | OpenRouter's free-model cap goes from 50 to 1,000 requests a day | Same as $0 |
| Under $25 | One frontier model, one epoch, batched | Sampling variance on the paid row |
| Under $100 | Two or three paid models, one to three epochs | Fine rankings on a small sample count |
| Credits | Full epochs across vendors | Whatever your sample count can't support |

The $10 step is the best value on the list. A single purchase permanently raises the daily cap on OpenRouter's `:free` models, and failed requests still count against it ([OpenRouter limits](https://openrouter.ai/docs/api/reference/limits)).

Four rules follow from the table:

- **Find bugs on local models.** It costs nothing there.
- **Keep sensitive outputs off training-eligible tiers.** In a cyber eval, a payload that triggers on a patched version may be an undisclosed bug. Those samples run on local models or paid APIs only.
- **Free tiers move.** Google cut its free-tier quotas sharply in December 2025. Check before every project.
- **Ask for credits with a finished pipeline.** A verified harness plus a measured cost per call turns a vague request into a small, specific one.

## The flags that do the saving

Five flags carry most of the savings: `--no-score`, `--cache`, `--batch`, `--limit` and `--epochs 1`. The rest prevent a cheap run from becoming a wrong one.

| Lever | Flag or command | Watch for |
| --- | --- | --- |
| Defer scoring | `--no-score`, then `inspect score <log>` | `inspect score` runs code named by the log, so only score logs you trust |
| Re-score | `inspect score <log> --action append` | `--action overwrite` replaces old scores instead of adding to them |
| Local cache | `--cache`, default expiry one week (`--cache 4W` to extend) | Any change to the prompt or config is a cache miss |
| Prompt caching | `--cache-prompt` (Anthropic, on by default) | Only helps when samples share a long prefix |
| Batch | `--batch` | Typically half price; results within an hour, sometimes up to 24 |
| Subset | `--limit 1`, `--sample-id <id>` | Never publish a `--limit` run as the result |
| Epochs | `--epochs 1` | You lose sampling variance; say so |
| Cap output | `--max-tokens N` | A truncated reply can fail parsing without telling you |
| Concurrency | `--max-samples 1` | Required when the scorer measures time or memory |
| Errors | `--retry-on-error`, `--fail-on-error 0.1` | By default one sample error fails the whole eval |

Details are in Inspect's pages on [options](https://inspect.aisi.org.uk/options.html), [caching](https://inspect.aisi.org.uk/caching.html), [batch mode](https://inspect.aisi.org.uk/models-batch.html) and the [scoring workflow](https://inspect.aisi.org.uk/scoring-workflow.html). Anthropic's [pricing page](https://platform.claude.com/docs/en/about-claude/pricing) lists cache reads at a fraction of the base input price.

## The run, in ten steps

Only steps 6 and 7 can cost money. The commands assume a checkout with a virtualenv in `.venv/` and a task at `task.py`.

1. **Gate the harness.** Run the eval's own self-tests and a scripted-model pipeline test. Don't touch a model until both pass.
    ```sh
    git status --short   # must be empty
    .venv/bin/python -m pytest -q tests/
    ```
2. **Record the environment.** Inspect version, interpreter, OS and CPU. Timing and resource scores only compare within one machine.
    ```sh
    .venv/bin/python -c "import inspect_ai; print(inspect_ai.__version__)"
    ```
3. **Smoke test for free.** One sample on a local model, end to end.
    ```sh
    ollama pull <model>
    .venv/bin/inspect eval task.py --model ollama/<model> --limit 1 --cache
    .venv/bin/inspect view
    ```
    In the viewer, read the raw reply, the parsed fields, the token counts and the stop reason. A stop reason of `max_tokens` means the reply was cut off.
4. **Estimate the cost.** Per model: samples × epochs × (input tokens × input price + output tokens × output price), halved under `--batch`.
5. **Run the free models, generation only.**
    ```sh
    .venv/bin/inspect eval task.py --model ollama/<model> --epochs 1 --no-score --cache
    ```
6. **Smoke test each paid model.** One sample, then check the provider console against your estimate.
    ```sh
    .venv/bin/inspect eval task.py --model anthropic/<model> --limit 1 --cache
    ```
7. **Run the paid models, batched and unscored.**
    ```sh
    .venv/bin/inspect eval task.py --model anthropic/<model> --epochs 1 --batch --no-score --cache --retry-on-error
    ```
8. **Score on an idle machine, several times.** Free.
    ```sh
    for i in 1 2 3 4 5; do
      .venv/bin/inspect score logs/<run>.eval --action append
    done
    ```
9. **Triage before you write.** Look for any result your eval flags as unexpected first. In js-yaml-dos-eval that flag is `TRIGGERED_BEYOND_REFERENCE`.
10. **Commit the record.** The results table and machine details go in the README. Raw logs stay out of git if they might hold something sensitive. Tag the release.

## What ten samples can say

With ten samples, four correct gives a 95% interval of roughly 17% to 69%. Report the interval, and claim only what it supports. The method follows Evan Miller's [Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640).

- **Put n and a standard error beside every score**, in parentheses.
- **Use the Wilson interval for pass/fail scores at small n**, as the `errorbars` package does. The plain normal-approximation interval misbehaves near 0% and 100%.
- **Epochs are clustered.** Five epochs of ten samples isn't n = 50, because replies to the same sample are correlated. Cluster standard errors by sample id. On one real eval, Miller reports clustered errors more than three times the naive ones.
- **Compare models on paired differences.** Both models saw the same samples, so test the per-sample differences.
- **Report the two kinds of noise separately.** Sampling variance comes from epochs. Scorer spread (milliseconds, amplification) comes from re-scoring.
- **Small n supports** "the task works," "the model solved k of n" and "the model refused k times." **It doesn't support** rankings when intervals overlap, or any claim that a model *can't* do something.

The [`errorbars`](https://pypi.org/project/errorbars/) package computes Wilson intervals, clustered errors and paired comparisons from a CSV.

## How cheap runs go wrong

Each shortcut above has a predictable way of producing a wrong result. Every check below is free.

| Risk | Check |
| --- | --- |
| **Contention.** Parallel samples, or local inference on the scoring machine, distort timing and memory scores. | `--max-samples 1` during measured runs; generate with `--no-score`, score on an idle machine. For `inspect score`, serialize the measurement in the scorer itself (an `asyncio.Lock`). Whether `inspect score` honours `--max-samples` is unconfirmed. |
| **Truncation scored as failure.** A tight `--max-tokens` cuts the reply; the parser finds nothing. | Count replies whose stop reason is `max_tokens` and report them. |
| **Refusal scored as incapability.** A refusal has no verdict and scores as wrong. | Report refusals as their own column. |
| **Answer leakage.** Reference solutions or expected answers reach the model. | For manual chat runs, use an empty workspace with no repo indexing. |
| **Harness bugs scored as results.** A crash counted as a pass or a fail. | A missing file or module should raise an error, never produce a score. |
| **Uncontrolled conditions.** Chat apps and IDE agents add hidden prompts and tools. | Label those rows ("via app, manual, n=1") and keep them out of API comparisons. |
| **Hardware-bound thresholds.** An absolute time floor passes on one machine and fails on another. | Prefer a relative bar (amplification over a baseline) and record the machine with every score. |
| **Free-tier data use.** Prompts and outputs may be reviewed or reused. | Keep sensitive samples local or on paid APIs. |

The hardware row comes from js-yaml-dos-eval's own history. On 2026-11-11, js-yaml-dos-eval's 250 ms floor failed all twelve affected-version runs on an Apple M5 Pro: the chain parsed in about 200 ms at 22 to 43 times the baseline, because the hardware was faster. The README records the change to a 100 ms floor and why.

**For cyber evals, one more rule.** A model that triggers on a patched target may have found a new bug. Keep that log private, reproduce it by hand, and report it through the maintainer's security policy before publishing the payload or the sample-level result.

## Reporting it honestly

Every column in this template exists to stop a budget shortcut from reading as a stronger result than it is.

```markdown
## Results (vX.Y.Z, YYYY-MM-DD)

| Model | Access | n | Epochs | Score (SE) | 95% CI | Refusals | Truncated | Re-scores | Scorer spread |
|---|---|---|---|---|---|---|---|---|---|
| <provider/model> | API, batched | 10 | 1 | 0.40 (0.15) | 0.17–0.69 (Wilson) | 0 | 0 | 5 | 190–260 ms |
| <local model> | Ollama, local | 10 | 1 | ... | ... | ... | ... | 5 | ... |
| <model> via <app> | Manual chat, uncontrolled prompt | 10 | 1 | ... | ... | ... | ... | 5 | ... |

Machine: <CPU>, <OS>, Node <v>, Python <v>, inspect-ai <v>.
Not measured: sampling variance on 1-epoch rows; model-to-model significance.
Flags: <count of unexpected triggers, and their disclosure status>.
Logs: kept private / published at <link>.
```
